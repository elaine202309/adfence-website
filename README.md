# AdFence — marketing website

Static marketing site for the Safari ad blocker (iPhone / iPad / Mac).
No framework, no build step, no dependencies. Plain HTML + one stylesheet.

> **Name: AdFence**, settled 10 October 2026 after checking the App Store and the
> open web for conflicts. No same-name app, no same-name ad-blocking extension,
> no software trademark found. This is not a legal clearance — see the comment
> block at the top of `index.html` for the caveats and the one remaining
> pre-submission step.
>
> **App Store display name: "AdFence - Ad & Tracker Blocker"** (changed 8
> November 2026; exactly 30 characters, the field limit). The name field has no
> room for "Safari", so Safari is carried by the subtitle ("Safari ad blocker for
> iPhone"), by the first keyword in every locale, by every page `<title>`, and
> by the footer line — "An ad and tracker blocker for Safari on iPhone, iPad and
> Mac." Keep that arrangement if you edit any of them. Renaming does not change
> the App Store URL: the `adfence-safari-ad-blocker` slug is fixed from when the
> app was created.

## Renaming (if you change your mind)

The name was settled as **AdFence** on 10 October 2026 — see the comment block at
the top of `index.html` for what was and wasn't checked. If you ever swap it
again, everything is relative-path based, so the only work is a find-and-replace:

```bash
grep -rl 'AdFence' . --exclude-dir=.git | xargs sed -i 's/AdFence/YourName/g'
```

Then fix by hand, because word order varies:

- Every `<title>` and `og:title` — e.g. `AdFence — Safari Ad &amp; Tracker Blocker for iPhone, iPad &amp; Mac`
- The footer brand line under the logo on all seven pages, and the header
  `<span class="brand-desc">` (short form, "Ad &amp; Tracker Blocker")
- The `"name"` field in the JSON-LD block in `index.html`
- `<meta property="og:site_name">` if you add one

If the new name has a different first letter, check the brand mark: it's an
inline SVG shield, not a letterform, so it survives renaming unchanged.

## Adding a blog post

1. Copy `blog/why-safari-ad-blocker-not-working.html` to `blog/<slug>.html` —
   lowercase, hyphens, and the question the post answers rather than a pun.
2. Change the `<title>`, `description`, `canonical`, the `og:`/`twitter:` tags,
   the `BlogPosting` node in the JSON-LD, the breadcrumb name, the `.post-meta`
   line (category · date · reading time) and the `<h1>`. Paths inside `blog/`
   are one level up: `../css/style.css`, `../images/…`, `../blog.html`.
3. Rewrite the FAQ at the bottom of the post — questions, answers, and the
   matching `FAQPage` entries in the JSON-LD. Delete it if the post genuinely
   has no questions worth answering.
4. In `blog.html`, move the current `.post-feature` markup into a
   `<a class="card post-card">` inside `.post-grid`, put the new post in the
   feature slot, and add it to the `blogPost` array in `blog.html`'s JSON-LD.
5. Add the new URL to `sitemap.xml` with today's `<lastmod>`, and add a line
   under "## Pages" in `llms.txt`.
6. Add the post to the `POSTS` array at the top of `tools/build-i18n.js`
   (newest first) and add a matching `blog.posts[]` entry — localized `date`
   and `readTime` — to all nine `tools/i18n/pages/*.json`, then re-run the
   generator. The build throws if the counts disagree, which is the only thing
   stopping the nine localized blog indexes from going stale.

There is no RSS feed and no build step; the index is hand-maintained on purpose,
so what is on the page is exactly what exists.

### Cloudflare

The domain is proxied by Cloudflare, so two settings there live outside this
repo and outside GitHub:

- **AI crawlers.** `robots.txt` allows everything, but Cloudflare can block bots
  at the edge anyway — Bot Fight Mode, "Block AI bots", AI Crawl Control. No
  error appears in Search Console if it does; the crawlers just never arrive.
  Check this before concluding that an AI engine is ignoring the site.
- **Always Use HTTPS.** `http://` does not redirect to `https://` at the moment,
  and GitHub's certificate reads as null while the record is proxied. Turning on
  Always Use HTTPS in Cloudflare SSL/TLS → Edge Certificates is the fix.

Verification trick while the domain is proxied: `curl --resolve` against port
80 works, HTTPS against the GitHub IPs does not, because GitHub holds no
certificate for a hostname it never sees.

## Notes for future edits

- All paths are **relative**, not root-absolute. This is deliberate — it means
  the site works at a GitHub Pages project URL (`user.github.io/repo/`) and at a
  custom domain without changes. Don't reintroduce `/css/style.css` style paths.
- Design tokens live in the `:root` block of `css/style.css`. Change the accent
  colour in one place there rather than hunting through the pages.
- The stylesheet is linked as `css/style.css?v=8`. **Bump that number whenever
  you change the CSS** — in all seven English pages (`../css/…` in `blog/`) and
  in `CSS_VERSION` at the top of `tools/build-i18n.js`, then re-run the
  generator. GitHub Pages sends `Cache-Control: max-age=14400` and Cloudflare is
  in front of it, so an unchanged URL can keep serving the old stylesheet for up
  to four hours after a deploy — long enough to make a layout fix look like it
  never shipped.
- **Localized pages.** `/zh-hans/ … /es/` are generated, not edited:

  ```
  node tools/build-i18n.js
  ```

  Four pages per language: homepage (copy in `tools/i18n/<slug>.json`), and
  how-to-use, support, blog (copy in `tools/i18n/pages/<slug>.json`, shape
  documented in `tools/i18n/pages/SCHEMA.md`). A new language is two JSON files
  plus one row in `LANGS`. Array lengths are checked and the script throws
  rather than writing a page with a hole in it: 15 / 4 / 4 / 3 / 5 / 6 on the
  homepage, 5 steps, 3 quick fixes, 2 setup cards of 5 items each and 5
  troubleshooting entries on the other three. **When you change the markup of
  an English page, change the matching template in `build-i18n.js` in the same
  commit**: English is hand-maintained and is the source of truth for structure,
  and the two drift apart silently otherwise.
- Hreflang is reciprocal across all four page types — English `how-to-use.html`
  lists `<slug>/how-to-use.html`, and each localized page lists all ten. If you
  add a page that exists in every language, add it to `LOCALIZED_PAGES`-style
  handling and to the alternates in the English page too. `privacy.html`,
  `terms.html` and the blog post are English-only: they carry the language menu
  (pointing at the nine homepages) but no hreflang, so Google is not told a
  translation exists.
- The consent banner in `js/analytics.js` picks its wording from `<html lang>`,
  so a new language also needs a row in its `COPY` object.
- The FAQ accordion auto-closes other items (`js/main.js`). If you want several
  open at once, delete that block.

- Structured data is hand-written JSON-LD in each page's `<head>`, one
  `@graph` per page. The `Organization` node has a fixed `@id`
  (`https://adfence.mxcode.com/#organization`) and the other nodes point at it
  instead of repeating it, so search engines and AI assistants resolve one
  entity across the whole site. `index.html` carries Organization + WebSite +
  SoftwareApplication + FAQPage; `support.html` and the blog post carry
  FAQPage; every page except the homepage carries a `BreadcrumbList`.
  **If you change the questions shown on a page, change the matching `FAQPage`
  entry in the same commit** — structured data that disagrees with the visible
  page is worse than none at all.
- `llms.txt` is a plain-text brief for AI assistants. It is not read by Google,
  and no ranking depends on it, but it is cheap and it is what an assistant
  quotes when someone asks what AdFence is. Keep the "Key facts" section true;
  it repeats the privacy claims.
